# Supported contract, schema 1

RankReserve 1.0 supports one sampling occasion, one required completion per site, fixed independent replacement pools, a shared campaign protocol/reference and completion definition, and one authoritative local coordinator database. Each reserve belongs to exactly one pool. All bases begin active. A design authority must supply and approve the ordinal sequence and pool boundaries; the software only executes that supplied policy.

## Input

UTF-8 CSV (a UTF-8 BOM is accepted), exactly `site_id,pool,rank,role` plus optional `label`, in any column order. Identifiers are case-sensitive; no normalization or fuzzy matching occurs. `role` is exactly `base` or `reserve`. Rank is a positive decimal integer, unique across both roles within a pool, and every base rank precedes that pool's reserve ranks. Ranks may have gaps. Every pool has at least one base. The target is the base count and is fixed after creation. There is no import of previous field outcomes; begin the ledger before campaign execution. Unplanned historical observations can be preserved as incidents, which hold activation for review.

IDs and pools are nonempty plain text up to 128 characters. Labels are at most 500 characters. Surrounding whitespace and control/format characters are rejected. Actor is at most 200 characters; notes/approval assertion at most 4,000; protocol reference/completion definition at most 2,000. These are required. Observation dates must be valid `YYYY-MM-DD` calendar dates. Dates are recorded evidence: revisions determine state and backdated observations do not reorder earlier decisions. A reserve's `sampled` observation date must be on/after its activation decision date, including amendments; earlier sampling must be recorded as an incident. Historical nonfinal evaluation notes are allowed. Day granularity cannot prove same-day chronology. The application records an independent UTC storage timestamp. A future observation date is not interpreted as a scheduling instruction.

Limits: 5,000 sites, 10 MiB encoded design CSV, 50,000 events, and 64 MiB database file. Oversized, malformed or foreign-version inputs fail with an error. Operation is intended for small local campaigns; split scientifically independent campaigns only with design-authority approval. Resource bounds are guardrails, not performance or availability guarantees.

## State and evidence

Initial campaign revision is 0; each accepted event advances it by one. Every mutation requires `--expect` equal to the current campaign revision. There is no automatic retry after stale data: first inspect and reconcile the observation. `--amend` references the site's latest **outcome** event, which can differ from its latest activation or the campaign's current revision.

Snapshot schema: `metadata`, `revision`, `pools`, `sites`, `queue`, `events`, `head_hash`. Metadata includes schema version, campaign UUID, canonical design, initial actor, approval note, protocol reference, completion rule and creation timestamp. A site retains original fields, active flag, current status, last state revision, last outcome revision, and incident revisions. Queue is the active unfinalized subset, not a route or an access authorization. Full event records carry kind, site, status, actor, reason, observation date, recorded timestamp, amendment reference and chain hashes.

Pool summary includes target, sampled count, unresolved active commitments, open slots, overcommitted count, remaining reserves, incident count and state. State precedence is `exception`, `conflict`, `complete`, `exhausted`, `needs_reserve`, `in_progress`. Open slots = max(target − sampled − unresolved, 0). Overcommitted = max(sampled + unresolved − target, 0). A pool can have a visible deficit while another pool is complete; substitution across pools is never inferred.

`exhausted` means a deficit with no unused reserve: consult the design authority. `exception` and `conflict` block new activation in that pool. Corrections and evidence exports remain available. No flag proves statistical validity or obviates weight adjustment by the analyst. Incidents do not count as successful completions or rejections and cannot be cleared in v1.

## Persistence and failure

Each write validates and replays the ledger, checks the expected revision, and appends within one SQLite transaction. Writes use an immediate transaction, local storage, SQLite's normal locking, and full synchronization. Interrupted uncommitted writes roll back. Corrupt JSON, incompatible schema, altered hash chain or impossible history fail closed. The hash chain detects some accidental modifications, not authenticity or all deletion: removing an unanchored trailing suffix can look like an earlier valid database. Exported head/revision records can help compare known snapshots. Keep trusted backups; never call this tamper-proof.

Existing paths are never overwritten by initialization, backup, examples or export. Normal caught export failures clean up the newly created directory; an abrupt process/power failure can leave an incomplete directory, identifiable by its missing manifest. After any uncertain interruption or receipt/output error, inspect the revision before retrying: a commit can succeed before its result is delivered. Read-only clean storage supports inspection but cannot accept mutations. Recovery of a hot rollback journal requires a writable database and directory; inspection/backup narrowly retries SQLite's rollback recovery without appending a human outcome. Keep the journal with its database until recovery completes. WAL databases and symlink database paths are rejected. A locked write reports failure after roughly five seconds rather than waiting indefinitely. All OS file permissions remain the operator's responsibility.

## Explicit exclusions

No survey draw generation, nearest-neighbor replacement, changing targets, shared reserves, dependent panels, panel cascades, unequal quota enforcement, revisit/inherited sampling obligations, design-weight adjustment, inference, GIS suitability, route optimization, measurement storage, access-permission automation, EPA submission integration, or multi-device merging. There is no arbitrary NARS/spsurvey workbook ingestion. Map original IDs and approved order explicitly, retain the source design separately, and keep unrelated fields there. Native NARS protocols have exceptions this schema cannot represent; no EPA compatibility or endorsement is claimed.
